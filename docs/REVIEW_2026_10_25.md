# SignBridge review — 25 October 2026

Review began 25 October; final verification completed 26 October 2026.

## Decision

Keep the present small-vocabulary landmark approach while collecting evidence. The immediate problem is insufficient, unverified data and uncertain customer value. A larger model or more features would not answer either question.

The current service demonstration uses a Help sign followed by buttons. That must be compared with simply offering an accessible help button or a human interpreter. Until Deaf users prefer the signing route in a real situation, the commercial advantage is a hypothesis.

The current return message is English text. The supported target group therefore needs to be ASL users who can read that output. It cannot honestly be described as a conversation service for every Deaf person or every UAE sign-language user.

## Actual local evidence

Checked without training on or modifying the participant's records:

- One training person.
- Hello: 32 samples; Help: 7; Water: 33; Again: 31; OTHER / NO SIGN: 5.
- Zero Final-test attempts.
- Zero real service tasks or recorded service journeys.

These counts explain why more recordings of Hello or Water are not the immediate priority. Correct Help examples, varied unknown movements and separate test people are much more useful. Thirty recordings is a starting suggestion, not an accuracy guarantee.

## Corrections implemented

1. **Confidence training:** scaling and PCA now fit inside each calibration split. Previously they could see the held-back calibration data. Training cross-validation is labelled as a development check, never as an independent Final test.
2. **Rejection:** when development data exists but no confidence threshold meets the precision, coverage and unknown-rejection targets, camera acceptance is paused. It no longer falls back to a threshold that failed. With insufficient people, the default remains explicitly unvalidated.
3. **Same rules in testing:** Final test applies the same minimum hand visibility as normal recognition. Poor visibility and failed camera captures remain in the report. Capture failures have their own count.
4. **Remote testing:** Final test accepts one short, labelled video. It stores the result, source type and a file fingerprint, not the video or its landmarks. Training and test people are checked against both current samples and the model's saved training-person list.
5. **Duplicate protection:** exact file fingerprints block reuse across training and testing, duplicate tests of one clip with the same model, and reuse through the PopSign importer. Changing a person's ID does not bypass an exact-file check. This is not face recognition: re-encoded/cropped copies and the same person under a different ID still require human checking.
6. **Service evidence:** journeys start at the first sign-recording request or manual selection. They count rejected attempts, manually rejected suggestions, manual fallbacks, abandoned input and guest-confirmed outcomes. Timing ends at guest resolution and includes capture, correction, confirmation and staff time. Reports identify older tasks without journey data instead of inventing missing timings.
7. **Saving and recovery:** failed task writes roll back the in-memory change and leave the request confirmable. No speech or notification occurs when task creation fails. Stalled or empty captures release the controls. Closing waits for running workers to finish safely. Incorrectly shaped task/settings files are left untouched and reported.
8. **Small-window layout:** test actions use short labels, section titles wrap, and horizontal scrolling remains available as a fallback. The Final-test page fits the minimum 960 × 640 window.

## Use the updated build

1. Start the app using the launcher in the main project folder.
2. Open Train model and retrain ASL once. Older calibration models are deliberately not loaded; their saved samples remain available.
3. In Final test, enter the tester's consistent ID, expected sign, condition and permission confirmation.
4. Choose Record attempt or Import test video. Use one sign per clip, preferably 2–5 seconds; the importer has a 12-second limit.
5. For service trials, use Competition demo. Finish one full guest/staff interaction and ask the guest whether it was resolved.
6. Export the aggregate report from Staff desk. It now includes input failures and first-attempt-to-resolution timing.

The original source videos remain wherever the user saved them. SignBridge does not copy or delete those files. Use only consented or properly licensed material and keep one ID per person across all sources.

If Final-test results influence model or threshold changes, treat them as development feedback. Use fresh untouched evidence to support a claim about the revised model.

## Verification and limits

- 88 automated tests cover the updated paths, including file-write failures, calibration splits, video/test separation, visibility rejection, service timing, duplicate protection, worker shutdown and the compact layout.
- A 26 October smoke test exercised the real MediaPipe importer with a generated blank video: it produced the expected 32-step features, a file fingerprint and zero hand visibility. This checks the actual video/model interface; it is not a sign-recognition accuracy test.
- Test and Staff-desk screens were rendered at normal size; Final test was also checked at 960 × 640 with actual Windows fonts.
- The webcam was not opened during this review. Automated tests and synthetic examples are not real sign-language accuracy results.
- Personal training samples and existing model files were not deleted or retrained.
- Existing sharing ZIPs were not rebuilt; use the updated main project folder until a fresh distribution is prepared.

## Next work

1. Have a fluent ASL signer validate Help and the other exact sign forms.
2. Improve the weak Help and unknown classes; reserve at least two, preferably three, entirely different test signers.
3. Test recognition with their live attempts or permitted short videos.
4. Run at least 20 complete desk trials and compare the journey with a simple help-button alternative.
5. Use target-user and buyer feedback to decide whether to proceed with the hotel workflow and an Initiate application.
